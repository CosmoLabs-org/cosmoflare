# D1 Depth: Migrations, Time-Travel Restore, Backups, Export/Import

**Created:** 2026-09-11T12:00:00+04:00
**Issue:** FEAT-022 | **Roadmap:** ROAD-091
**Status:** design complete

## Why

Today `cmd/d1.go` ships five commands: create, list, get, delete, query.
That covers basic CRUD. Production D1 usage requires four more capabilities:
schema migration management, point-in-time recovery (time-travel), database
export for backup/portability, and database import for restore/seeding.
Without these, users fall back to raw wrangler commands or hand-rolled
scripts (evidence: FEAT-018 MyCarGuide session, 35MB seed required a custom
batcher).

The Qwen D1 mapping corpus
(`docs/research/2026-09-10-cf-limits-corpus/qwen-results-d1-mapping.md`)
documents every wrangler D1 command and its API endpoint. The D1 security
corpus (`qwen-results-d1-security.md`, sections 6-7) prescribes production
SQL execution guards, migration token separation, and dry-run discipline.
These shape every command below.

## Existing foundation

- `pkg/cosmoflare/d1.go` — `D1Service` with Create, List, Get, Delete,
  Query methods wrapping `cloudflare-go`. Types: `D1Database`,
  `D1QueryResult`, `D1QueryMeta`.
- `cmd/d1.go` — cobra commands for the five verbs above. Uses
  `getD1Service()`, `printSuccessJSON`, `printErrorJSON`, `DryRun`,
  `JSONOutput`, `d1Force` flag patterns.
- `pkg/cosmoflare/errors.go` — `isNotFound()`, `validationError()`,
  `newError()`, `authError()` helpers.
- Limits awareness layer brainstorm
  (`docs/brainstorming/2026-09-10-cf-limits-awareness-layer.md`) — BR-04
  specifies D1 usage tracking rows. The time-travel restore rate limit
  (`d1.time_travel_restores`: 10 per 10 min per DB, hard quota) is already
  in the limits catalog (`qwen-results.md`, section 4, edge case 6).

## Design decisions

### D1 — Migration state tracking

**Question:** Where does the applied-migrations ledger live?

**Decision:** In a `d1_migrations` table inside the D1 database itself.
This matches wrangler's convention (qwen-results-d1-mapping.md, section
4.2). No local file — the database is the source of truth for what has been
applied.

**Schema:**

```sql
CREATE TABLE IF NOT EXISTS d1_migrations (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  name       TEXT    NOT NULL UNIQUE,
  applied_at TEXT    NOT NULL
);
```

**Justification:**
- Wrangler compatibility: users who switch between cosmoflare and wrangler
  see the same migration state.
- No local state drift: multiple machines/agents can apply migrations and
  see consistent state.
- The `name` column stores the migration filename (e.g.
  `0001_create_users.sql`). `applied_at` is ISO8601 with timezone.

**Local migrations directory:** `migrations/` relative to project root (or
configurable via `.cosmoflare.yaml`). Numbering: `NNNN_description.sql`
(zero-padded 4-digit prefix, sequential). `migrations create` generates the
next number automatically.

### D2 — Time-travel restore UX

**Question:** What is the restore flow and how does the quota work?

**Decision:** Two-step flow: bookmark → restore.

```text
cosmoflare d1 time-travel restore <database> --timestamp "2026-09-10T14:00:00Z"
```

**Quota pre-flight:** Before issuing the restore API call, the CLI checks
the remaining restore budget. The D1 time-travel restore limit is 10
restores per 10 minutes per database (hard quota, not daily — edge case 6
in the limits corpus). The CLI cannot query exact remaining count from the
API (no endpoint exists), so it tracks restores locally in a lightweight
cache file (`.cosmoflare-time-travel-cache.json`) keyed by database ID +
timestamp window.

**CLI output after restore:**

```text
✅ Database 'my-app-prod' restored to 2026-09-10T14:00:00Z
   Restores used: 3/10 (in current 10-minute window)
   Window resets at: 2026-09-10T14:20:00Z
```

**Guards:**
- `--force` skips confirmation prompt.
- Default: interactive confirmation showing database name, ID, account,
  and target timestamp.
- `--dry-run` prints what would happen without calling the API.

### D3 — Backups vs time-travel

**Question:** Support legacy backups API, modern time-travel, or both?

**Decision:** Time-travel only, with a compatibility note. The legacy
backups API (`d1 backups list/restore`) is deprecated in favor of
time-travel. Cosmoflare ships `d1 time-travel restore` and documents that
users with older databases should use time-travel (available on all plans).
No `d1 backups` subcommand — avoids maintaining a deprecated surface.

**Justification:** Cloudflare has moved to time-travel as the canonical
point-in-time recovery mechanism. Adding legacy backup commands would
create confusion about which to use and require maintaining two code paths
for the same purpose.

### D4 — Export/import design

**Question:** How do export/import handle large databases?

**Export:**
- Format: SQL dump (CREATE TABLE + INSERT statements). This is the
  standard portable format and what wrangler produces.
- Streaming: The export API endpoint
  (`POST /accounts/{account_id}/d1/database/{database_id}/export`) may
  return data asynchronously. The CLI streams output to stdout or a file
  (`--output path`). No full-database buffering in memory.
- Size reality: D1 databases can reach 10GB on paid plans (0.94GB
  MyCarGuide evidence from FEAT-018). Export must handle multi-GB output.

**Import:**
- The import command MUST reuse the same statement-aware SQL splitter
  design specified in FEAT-018's `d1 push-sql` (`P0` item 1). That means:
  quote/comment/semicolon-aware splitting, byte-capped batches (~40KB),
  SQLITE_TOOBIG split-retry, retry-with-backoff on error 7500, progress
  lines, kill-safe resume via INSERT OR IGNORE idempotency.
- **This design references FEAT-018, not duplicates it.** FEAT-018 builds
  the splitter (`d1 push-sql`); FEAT-022's import wraps it for the
  full-database restore use case. If FEAT-018 ships first, import calls
  the same library function. If FEAT-022 ships first, the splitter is
  built here and FEAT-018's `push-sql` becomes a thin CLI wrapper.
- Import target: `--db <name-or-id> [--remote|--local]`.

**Format decision:** SQL dump only (no NDJSON). SQL is the lingua franca
for SQLite-compatible databases. NDJSON adds complexity with no clear
benefit for D1's use case.

### D5 — Local vs remote semantics

**Question:** How does every new verb handle local vs remote?

**Decision:** Every new command accepts `--local` and `--remote` flags,
matching wrangler's convention (qwen-results-d1-mapping.md, section 8).

| Command | `--local` behavior | `--remote` behavior |
|---|---|---|
| `migrations create` | Creates file in `migrations/` dir | Same (local-only operation) |
| `migrations list` | Scans local dir + queries local DB | Scans local dir + queries remote DB |
| `migrations apply` | Applies to local SQLite D1 | Applies to remote Cloudflare D1 |
| `time-travel restore` | Not supported (local has no time-travel) | Restores remote DB to timestamp |
| `export` | Exports local SQLite DB | Exports remote D1 via API |
| `import` | Imports into local SQLite DB | Imports into remote D1 via API |

**Default:** `--remote` when no flag given. The CLI prints which target is
active before executing (security corpus section 6: "make this explicit in
every D1 command").

### D6 — Safety guards

**Question:** Which verbs require confirmation, and what is the --dry-run
surface?

**Decision per the D1 security corpus (sections 6-7):**

| Command | Confirmation | `--dry-run` | `--force` bypass |
|---|---|---|---|
| `migrations apply --remote` | Yes (type DB name) | Yes (list pending, don't execute) | Yes |
| `migrations apply --local` | No | Yes | N/A |
| `time-travel restore` | Yes (type DB name) | Yes (show target timestamp) | Yes |
| `import --remote` | Yes (type DB name) | Yes (parse file, show stats) | Yes |
| `import --local` | No | Yes | N/A |
| `export` | No (read-only) | No | N/A |
| `migrations create` | No (local file only) | No | N/A |
| `migrations list` | No (read-only) | No | N/A |

**Destructive SQL detection in migrations:** The `migrations apply` command
scans each pending migration for destructive statements (DROP TABLE,
DELETE without WHERE, ALTER TABLE DROP COLUMN) and prints a warning before
the confirmation prompt. This follows the security corpus section 7:
"Keep destructive migrations explicit."

**Separate migration tokens:** The security corpus recommends separate
tokens for migrations vs deployment. Cosmoflare supports this via
`--api-token` flag override or `.cosmoflare.yaml` per-environment token
configuration (ties into FEAT-026 environment profiles).

## Command structure

Following the recommended structure from qwen-results-d1-mapping.md
section 10:

```text
cosmoflare d1 migrations create <database> <migration-name>
cosmoflare d1 migrations list <database> [--local|--remote]
cosmoflare d1 migrations apply <database> [--local|--remote] [--dry-run] [--force]

cosmoflare d1 time-travel restore <database> --timestamp <ISO8601> [--dry-run] [--force]

cosmoflare d1 export <database> [--output file.sql] [--local|--remote]

cosmoflare d1 import <database> --file <file.sql> [--local|--remote] [--dry-run] [--force]
```

All commands support `--json` output.

## Permissions (from qwen-results-d1-mapping.md section 11)

| Command | Required permission |
|---|---|
| `migrations list` | D1 Read (queries d1_migrations table) |
| `migrations apply` | D1 Edit (executes SQL + writes d1_migrations) |
| `time-travel restore` | D1 Edit (mutates database state) |
| `export` | D1 Read |
| `import` | D1 Edit |

These feed the permdata manifest for required-permission notes per verb.

## Interoperability

- **Limits layer (BR-04):** D1 time-travel restore rate
  (`d1.time_travel_restores`) is already cataloged. The quota pre-flight
  in D2 uses this data. Import/export operations should report rows
  read/written for cost awareness (FEAT-018 design principle).
- **FEAT-018 push-sql:** Import shares the statement-aware splitter. See
  D4 above.
- **FEAT-026 environment profiles:** `--local`/`--remote` flags are the
  foundation. Named environment profiles will wrap these with config-driven
  defaults.
- **Existing patterns:** All new library methods go on `D1Service` in
  `pkg/cosmoflare/d1.go`. All new CLI commands register under `d1Cmd` in
  `cmd/d1.go`. Error handling uses `isNotFound`, `validationError`,
  `newError` from `pkg/cosmoflare/errors.go`.
